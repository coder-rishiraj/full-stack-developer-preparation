Chapter 2

Power BI: model, DAX, report, Service, Fabric

Power BI is five things that get taught as one, which is why people bounce off it. Separate them and it is straightforward: a model (tables and relationships), measures (DAX), a report (the visuals), the Service (publishing, security and refresh), and the modern Power BI ecosystem around Fabric, Copilot and governed semantic models. This chapter does all five, with a working DAX engine, a clickable report, interview answers, and practice scenarios that make filter context visible rather than mystical.

Install Power BI Desktop before starting. It is free and Windows-only. On a Mac you need Windows in Parallels, Boot Camp on older hardware, a borrowed Windows laptop, or a cheap cloud Windows machine. Everything on this page runs in the browser, but it is a model of Power BI, not a substitute — you need to have clicked the real thing before an interview.

The standard for this chapter. By the end you should be able to build a clean hiring semantic model, write the core measures without copying, design a one-page report, publish it, explain refresh and RLS, diagnose a slow visual, and answer a case interview about sharing sensitive HR data. If you can do those things out loud, you do not sound like someone who watched a dashboard tutorial. You sound like someone who can own reporting.

What it is actually for

Why Power BI, when Excel works

The honest summary to give in an interview: "Excel for analysis I am doing once, Power BI for a report other people need every week." That answer shows judgement; saying Power BI is simply better does not.

The three parts of the application. They are tabs down the left of Power BI Desktop, and knowing which one you are in solves most confusion.

  • Report view — the canvas. Visuals, slicers, layout.
  • Table view — the data, as a grid. Where calculated columns are added.
  • Model view — the tables as boxes with lines between them. Where relationships live.

Getting data in, properly

Power Query, again

Good news: the Get Data and Transform Data experience is the same Power Query you learned in chapter 1.4. Same ribbon, same Applied Steps, same transforms. Nothing new to learn.

  • Import vs DirectQuery. Import copies the data into the file — fast, and what you want in almost every case. DirectQuery queries the source live — slower, and for data too large or too sensitive to copy. If asked, the answer is Import unless the data is enormous or must not leave the source.
  • Do the cleaning in Power Query, not in DAX. This is the rule that separates a good model from a slow one. Splitting a column, trimming text, fixing types: Power Query. Calculating a rate that responds to slicers: DAX.
  • Close & Apply loads it into the model.

The data connection choices

ChoiceUse it whenInterview sentence
ImportThe normal case: Excel, CSV, ATS exports, small databases. Data is copied into the model and refreshed on a schedule."I default to Import because it is fast and stable for HR reporting."
DirectQueryThe source must stay live, the table is too large to import, or policy says data cannot be copied. Every click sends queries back to the source."DirectQuery is not a speed button; it is a source-policy and scale choice."
Live connectionThe company already has a governed semantic model or Analysis Services model, and you are only building the report layer."If the model already exists, I connect to it rather than redefining metrics."
Composite modelSome tables are imported and some stay DirectQuery. Powerful, but easier to make slow or confusing."I would use it only with a clear reason and test performance."
Direct LakeFabric-backed data lives in OneLake and the semantic model reads Delta tables directly without a normal import copy."Direct Lake is a Fabric pattern; for this course you only needs to recognise it."

Power Query skills that make your look senior. Append stacks same-shaped files; merge joins lookup data; unpivot turns month columns into rows; parameters stop hard-coded file paths; query folding means Power Query can push work back to the source database; privacy levels stop accidental data leakage across sources. You do not need to say all of that in one breath, but you should recognise every phrase.

The concept everything else rests on

The model, and star schema

A model is tables plus relationships. The shape to aim for has a name — a star schema — and it is simpler than it sounds.

One fact table in the middle, lookup tables around it, filters flowing inward.

  • Fact table — the events. One row per candidate application. Long and thin, and it grows.
  • Dimension tables — the lookups. One row per role, per recruiter, per date. Short and wide, and they describe things.
  • Relationships run one-to-many, from the one side (Roles) to the many side (Candidates). Filters flow in that direction: picking Dublin in Roles filters Candidates. The reverse does not happen by default, and that is deliberate.

How to create one

Model view, drag RoleID from Roles onto RoleID in Candidates. That is it. Power BI will often detect it automatically, which is convenient and worth checking rather than trusting.

ThingWhat to know
CardinalityOne-to-many is what you want. Many-to-many is a sign the model needs a bridge table and should be avoided while learning.
Cross-filter directionLeave it Single. Setting it to Both causes ambiguous filter paths and numbers nobody can explain.
Active relationshipOnly one can be active between two tables. If you need a second (applied date and joined date both to Calendar), the second is inactive and is switched on inside a measure with USERELATIONSHIP.
A date tableMark a proper Calendar table as the date table. Without one, time intelligence functions do not work properly. CALENDARAUTO() makes one in a line.
Hidden technical columnsKeys, sort columns and helper flags can be hidden from report view. The reader sees business terms, not plumbing.
Sort by columnMonth names sort alphabetically unless a MonthNumber column tells Power BI the real order.
Bridge tableUsed when the real world is many-to-many, such as candidates with several skills and roles requiring several skills. The bridge stores the pairs.

The single most common modelling mistake is putting everything in one wide table — every candidate row also carrying the role title, the city, the manager, the recruiter's team. It works on six rows and becomes unmanageable at scale: the same role title typed 400 times, no single place to fix it, and a Source slicer that cannot be built cleanly. If an interviewer asks about star schema, this is the answer: separate the events from the things, join on an ID.

The model checklist before any visual exists

  • Every relationship has an ID on both sides, not a text title that someone can spell three ways.
  • Fact tables contain events and numbers; dimensions contain the descriptions people slice by.
  • Columns are named for humans: Applied Date, not appl_dt_v2.
  • Raw source columns you do not want readers dragging into visuals are hidden.
  • Measures live in one place, ideally a dedicated Measures table, so the Fields pane is not a junk drawer.
  • The model has a documented grain: Candidates has one row per candidate application. Grain is the first sentence of trust.

The idea that unlocks DAX

Filter context

This is the whole thing. Every DAX measure is written once and gives a different answer in every place it appears, because a measure is evaluated against whatever rows are currently visible. Those visible rows are the filter context.

So COUNTROWS(Candidates) is not "6". It is "however many candidate rows the user can currently see". On a card with nothing clicked it is 6. In a table row for LinkedIn it is 4. With a Dublin slicer on it is 4. One formula, many answers.

Prove it — this is a real DAX engine

Click the slicers to change the filter context, then run the same measure again. Nothing about the formula changes; the answer does.

Where filter context comes from, all at once and all combining: the slicers on the page, the row and column a value sits in inside a table or matrix, a visual-level or page-level filter, another visual that has been clicked (cross-filtering), and anything a measure adds itself with CALCULATE.

Row context is the other one, and it is different. A calculated column is evaluated row by row, so inside it Candidates[Accepted] - Candidates[Applied] means this row's dates. A measure has no row context, which is why that same expression fails in a measure and needs an aggregator like AVERAGEX around it. If you can say that sentence in an interview, you are ahead of most candidates.

The functions and patterns that matter

Writing measures

DAX has hundreds of functions and a recruiting report needs a small, well-understood core. Here they are, grouped by what they are for. The point is not to memorise syntax like a poem; it is to know the pattern well enough to choose the right one under pressure.

Measures vs calculated columns, stated once. A calculated column is computed at refresh, stored in the file, and takes memory. Use it for a property of a row — days to hire, a seniority flag. A measure is computed at the moment of looking and stores nothing. Use it for anything aggregated or any ratio. When in doubt, write a measure — the mistake of storing a rate in a column is much more expensive than the reverse.

Measure branching is how experts stay sane. First write base measures such as Applicants, Offers, Accepts and Joiners. Then build ratios from them: Acceptance Rate = DIVIDE([Accepts], [Offers]). If the definition changes later, you edit one base measure instead of hunting through twenty visuals.

Write them yourself

These are graded against the real engine. Reference the tables as Candidates and the columns as Candidates[Name].

The one function worth real practice

CALCULATE, in detail

Everything else in DAX is ordinary. CALCULATE is the one that takes practice, because it does something no Excel function does: it changes the filter context before evaluating.

CALCULATE( what to work out , filter 1 , filter 2 , … )

Three things it does, in order of how surprising they are:

  1. It adds filters. CALCULATE(COUNTROWS(Candidates), Candidates[Source]="LinkedIn") counts only LinkedIn, wherever it is placed.
  2. It replaces filters on the same column. If the page is already sliced to Referral and the measure says Source = "LinkedIn", the answer is LinkedIn — the measure wins. This surprises everybody once.
  3. It removes filters, with ALL. CALCULATE(COUNTROWS(Candidates), ALL(Candidates)) ignores every slicer and gives the grand total. This is how a percent-of-total is built: the numerator respects the filter, the denominator does not.

Watch all three happen

Click the Referral slicer, then run each example in turn. The first follows the slicer, the second overrides it, the third ignores it entirely.

The percent-of-total pattern, written out, because it is the one you will use most:

Source share = DIVIDE( COUNTROWS(Candidates), CALCULATE(COUNTROWS(Candidates), ALL(Candidates)) )

The numerator is the current context — one row of a table, so one source. The denominator strips all filters, so it is always the full six. Put this measure in a table with Source in the rows and each line shows its share, totalling 100%.

A working report, in the browser

This is a model of your report page. Click the slicers. Every card, bar and matrix cell recalculates — and nothing beneath it was written per-visual. That is filter context doing the work.

Four report-building things that are not obvious.

  • Edit interactions (Format → Edit interactions) controls what happens when a visual is clicked. By default clicking a bar cross-filters everything else. Sometimes that is wrong — a summary card should usually stay put — and this is where it is switched off.
  • Drill-through lets a reader right-click a role and land on a detail page filtered to it. It is what turns a dashboard into something people explore instead of asking your about.
  • Bookmarks save a view — a set of filters and a layout. Useful for a "this is the story" button in a presentation.
  • Tooltips can be a whole report page. Hover a bar and a mini-report appears. Cheap, and it looks expert.

The layout rules, same as Excel

  • Cards across the top, charts in the middle, detail table at the bottom. People read top-left to bottom-right.
  • Chart titles are findings, not axis names. This matters more in Power BI because the title is the only text on the page.
  • One page. A second page is for drill-through detail, not for the overflow of page one.
  • Two colours and a grey. Use the theme, not hand-picked colours per visual.
  • Put the refresh date on the page. The first question anyone asks is how current it is.

Publishing, and the part interviewers probe

The Power BI Service

Desktop builds it; the Service is where other people use it. Knowing the vocabulary here is a disproportionate advantage, because most people who "know Power BI" have only ever used Desktop.

TermWhat it is
WorkspaceA shared folder where reports live. Permissions are set here. "My Workspace" is private and is not where team reports belong.
Semantic model (dataset)The model and measures, uploaded. Several reports can share one, which is the point — one definition of "time to hire" for the whole company.
ReportThe pages of visuals, connected to a semantic model.
DashboardA single page of pinned tiles, possibly from several reports. Older concept; the report is usually the better thing to share.
AppA packaged, published version of a workspace for a wide audience. What you would give a whole HR department.
Scheduled refreshUp to eight times a day on a Pro licence. Set it, and the report updates without you.
GatewayA small program installed on-premises so the cloud can reach a local file or database. The answer to "how does it refresh if the data is on our server?"
Row-level security (RLS)Different people see different rows of the same report. This is the HR answer. A hiring manager sees only their own requisitions. Set with a DAX filter on a role, tested with "View as role".
Sensitivity labelMarks a report Confidential and carries that into exports. Expected on anything with candidate or pay data.

Row-level security is the question you should hope for. HR data is the most sensitive data in a company — salaries, performance, candidate records. "How would you share a hiring dashboard with twenty managers without everyone seeing everyone's data?" The answer is row-level security: a role with a DAX filter such as Roles[HiringManager] = USERPRINCIPALNAME(), so each manager's own email filters the model to their own requisitions. One report, twenty different views, nothing duplicated.

Then add the thing that marks real experience: "and I would test it with View as role before publishing, because getting that wrong is a data breach, not a bug."

Sensitive HR data without panic

Security, governance and sharing

Power BI is not just making a page pretty. In a company it is a controlled way to let people see data they are allowed to see, using one agreed version of the numbers. This is where a Talent Acquisition Partner can sound unusually strong, because hiring data is full of names, salaries, notes, offers, rejection reasons and manager opinions.

ControlWhat you should knowHR example
Workspace rolesAdmin, Member, Contributor and Viewer control who can manage or only consume content.HR analytics team edits; hiring managers view.
AppThe clean way to distribute approved content from a workspace to a wider audience."Hiring Manager Pack" with one report and one help page.
EndorsementPromoted or Certified content tells people which report is trusted.Stop five different acceptance-rate reports circulating.
Sensitivity labelsMark content Confidential and carry protection into export paths where the tenant supports it.Candidate-stage and offer data should not be treated like a public headcount chart.
RLSFilters rows per viewer. The model stays one model; the visible rows change per user.A manager sees only their requisitions.
OLSObject-level security hides tables or columns.A viewer can see status and source but not offer salary or recruiter notes.

"I would share the app, not the workspace, use groups rather than individual permissions, label it Confidential, and use RLS for manager-specific views."

The report must update when you are asleep

Refresh, gateways and data quality

A report that refreshes cleanly is a product. A report that needs your to open a file every Monday is an ornament. Refresh is where many Power BI beginners fall apart because they built the page without thinking about where the data lives.

ProblemPower BI answerWhat to say
ATS export is saved to SharePoint every morning.Connect to the SharePoint/OneDrive file location, publish, schedule refresh."The path must be stable; the file cannot live on my Desktop."
Data sits in an internal SQL Server.Install and configure an on-premises data gateway."The Service needs a gateway to reach a private network source."
Refresh fails because a column was renamed.Check refresh history, fix the Power Query step, and add a data-quality check."Refresh history is the first place I look."
The table has years of history and refresh takes hours.Incremental refresh partitions the table and refreshes only the recent period."Refresh less data, not the same old data every time."
Different people use different definitions.Publish one shared semantic model and build reports from it."Governance means one definition of time to hire."

The minimum refresh checklist. Data source credentials set. Gateway online if needed. Scheduled refresh enabled. Refresh history checked after first publish. Owner set to a team account or workspace process, not one person's forgotten login. Page shows the last refresh date.

Fast reports feel trustworthy

Performance and troubleshooting

You do not need to be a Power BI engineer, but you should know the first moves when a report is slow. The impressive part is not naming every internal engine. It is having calm instincts.

SymptomLikely causeFirst fix
Every visual takes seconds to load.Too many visuals, too many high-cardinality fields, or DirectQuery hitting a slow source.Use Performance Analyzer, reduce visuals, test the expensive visual first.
File is huge.Unneeded columns, repeated text, high-cardinality IDs, calculated columns used where measures would do.Remove columns in Power Query, hide not enough; do not import what is not used.
Slicer has thousands of names.Wrong field for a slicer.Use role, city, recruiter, date range; not candidate name.
DAX measure is slow.Complex iterator over too many rows or bad model shape.Check the model first; star schema before heroic DAX.
Report breaks after refresh.Source schema drift, renamed headers, changed date type.Fix Applied Steps and add a small QA table of row counts and blank checks.

Performance sentence. "I would start with the model and the visual design: remove unused columns, keep the star schema, avoid high-cardinality slicers, use Performance Analyzer, and only then look for a clever DAX rewrite."

Modern Power BI features that sound real

These are not all required for your first report. They are the vocabulary that lets your survive a modern interview without pretending to be a Fabric architect.

The trap is feature-chasing. A weak model with Copilot is still a weak model. A confusing report with visual calculations is still confusing. The order is always: correct data, clean model, clear measures, readable report, governed sharing, then advanced features.

Only if there is time

PL-300, honestly

PL-300 is the Microsoft Power BI Data Analyst certification. It is a real, respected exam, and the current skills map is the same shape as this chapter: prepare data, model data, visualise and analyse data, and manage and secure Power BI assets.

But the order matters. A certificate with no file behind it is weaker than a file with no certificate. The sequence is: build the real report first, be able to talk about it, and only then consider the exam as a tiebreaker. If you have to choose between spending four weeks on PL-300 and four weeks building and explaining two real dashboards, you should build the dashboards.

What "I know Power BI" should mean when you say it. You have published a report to a workspace, set a scheduled refresh, can explain a star schema, can write measures for conversion and cost, can use RLS for hiring-manager views, and can name what you would check when refresh or performance breaks. That is a serious bar, and clearing it puts your ahead of most people who list Power BI on a CV.
